## 1. สำรวจโค้ดการวาด

### โครงสร้างที่เป็นอยู่

- ไม่มี bundler ไม่มี `package.json` · เป็น ES module 189 ไฟล์ (~44,000 บรรทัด) โหลดตรงผ่าน importmap ใน `index.html` · deploy = คัดลอก `src/ img/ audio/` ขึ้น GitHub Pages
- แผนที่วาดแบบ "สั่งวาดทุกเฟรม" (immediate mode): `ui.js frame()` → `scene.js render(ctx, …)` → ส่ง `ctx` ต่อให้ราว 25 โมดูล · ของที่ยืนบนพื้นถูกเก็บเป็นรายการ closure แล้วเรียงตาม y ก่อนวาด
- ฟังก์ชันวาดชุดเดียวกัน (`drawStandee`, `drawHeroWalk`, `drawCrewWalk`, `drawSoul`, `drawTownTerrain`) ถูกใช้กับ canvas อื่นด้วย: แผนที่ย่อ, ห้องสถานี, ชายแดน, ดันเจี้ยน — ทุกตัวเป็น Canvas 2D
- `scene.js` ดัก `ctx.drawImage` อยู่แล้ว (`installSpriteCache`) เพื่อ resample sprite คุณภาพสูงครั้งเดียว — แปลว่าจุดต่อระดับ `ctx` มีอยู่แล้วในโค้ด

### ก) PixiJS v8 — เขียนฉากแผนที่ใหม่เป็น scene graph

- **ข้อดี:** ไลบรารีโตแล้ว จัดการ batch / texture / context หลุด / RenderTexture ให้ · มีทาง WebGPU · มีคนใช้เยอะ หาตัวอย่างง่าย
- **ข้อเสีย:**
  - Pixi เป็นแบบ "สร้างวัตถุค้างไว้" แต่โค้ดเราเป็นแบบ "สั่งวาดทุกเฟรม" → ต้องเขียน `scene.js`, `art.js`, `town-*.js` ใหม่ (ราว 8,000–10,000 บรรทัด)
  - การรวมรอบวาดพื้น (ที่ให้ผลจริง 45%) Pixi ไม่ทำให้เอง ต้องเขียน shader เองอยู่ดี
  - ฟังก์ชันวาดที่ใช้ร่วมกับห้องสถานี/ชายแดน/แผนที่ย่อ ต้องแยกเป็นสองชุด
- **ขนาด:** `pixi.min.mjs` 8.23.0 = 913 KB (gzip 255 KB, brotli 203 KB) — วัดจากไฟล์ใน npm · เกมไม่มี bundler จึงตัดส่วนที่ไม่ใช้ออกไม่ได้ ต้องโหลดทั้งก้อน หรือเพิ่มขั้นตอน build ซึ่งเปลี่ยนวิธี deploy
- **ความเสี่ยงเทสต์:** สูง — ราว 60 ไฟล์ / 400 เทสต์ ที่ตรวจคำสั่ง `ctx` หรือข้อความซอร์สของ `scene.js`/`art.js` ต้องเขียนใหม่
- **Fallback Canvas 2D:** ในแพ็กเกจ 8.23.0 มี `CanvasRenderer` อยู่ (เห็นไฟล์) **ผมไม่ได้ทดสอบว่ารองรับครบแค่ไหน** · ถ้าไม่ครบ ต้องเก็บโค้ด 2D เดิมไว้ทั้งชุด = ดูแลสองระบบ
- **ทยอย deploy:** ยาก — Pixi ต้องเป็นเจ้าของ canvas ทั้งใบ จึงเป็นการเปลี่ยนครั้งใหญ่ครั้งเดียว

### ข) ผสม — เพิ่ม canvas WebGL ไว้ใต้ canvas 2D เดิม

WebGL วาดเฉพาะพื้น (+ แสงเรือง + ของเหลว) · canvas 2D เดิมโปร่งใสวางทับ วาดทุกอย่างที่เหลือเหมือนเดิม

- **ข้อดี:** งานน้อยที่สุด · กระทบเทสต์น้อย (~20 ไฟล์กลุ่มพื้น) · fallback ง่าย (ไม่มี WebGL ก็วาดพื้นลง 2D แบบเดิม)
- **ข้อเสีย:**
  - ได้ผลแค่ 22% เพราะเงาเมฆยังต้องวาดเต็มจอบน 2D และเบราว์เซอร์ต้องซ้อน canvas เพิ่มอีกชั้น
  - **ภาพจะเพี้ยนในจุดที่ใช้ blend พิเศษ:** แสงจุด, ของเหลว, effect กลางคืน ใช้ `screen` / `lighter` ผสมกับพื้น — เมื่อพื้นไม่อยู่ใน canvas เดียวกันแล้ว ผลผสมจะไม่เหมือนเดิม ต้องไล่ย้ายทีละชั้นตามลงไป
  - แสง normal map ทำได้แค่กับพื้น ทำกับอาคาร/ตัวละครไม่ได้ (ยังอยู่บน 2D)
- **ขนาด:** เพิ่มโค้ดราว 10–15 KB (ประเมิน)
- **ความเสี่ยงเทสต์:** ต่ำ
- **Fallback:** ดี

### ค) ตัววาด WebGL2 ของเราเอง ที่รับคำสั่งหน้าตาเดียวกับ Canvas 2D — **แนะนำ**

สร้างวัตถุ "ตัววาด GL" ที่มี `drawImage`, `save/restore`, `setTransform/translate/scale`, `globalAlpha`, `globalCompositeOperation`, `fillRect`, clip สี่เหลี่ยม เหมือน `ctx` ของ Canvas 2D · `scene.js render(ctx, …)` รับตัวนี้แทน · ทุกอย่างวาดลงเฟรมเดียว จึงผสมสีถูกต้องเหมือนเดิม
ของที่ WebGL ทำไม่ได้ (path, ตัวหนังสือ, gradient) ให้ canvas 2D เล็ก ๆ วาดแล้วส่งขึ้นเป็น texture ตามลำดับเดิม · จากนั้นเพิ่ม "ทางลัด" ให้ชั้นที่แพง (พื้น, เงาเมฆ) ใช้ shader รวมรอบ

- **ข้อดี:**
  - โค้ดวาดเดิมไม่ต้องเขียนใหม่ ลำดับชั้น/การบังกันเหมือนเดิม
  - Fallback ได้ฟรี: ส่ง `ctx` 2D ตัวจริงเข้าไป = เส้นทางเดียวกับวันนี้ทุกบรรทัด
  - ฟังก์ชันวาดที่ใช้ร่วมกับห้อง/ชายแดน/แผนที่ย่อ ใช้ต่อได้โดยไม่แตะ
  - ได้ผลเต็ม 45% เมื่อรวมรอบ (ตาม prototype) และเป็นเจ้าของ shader เอง → ต่อ normal map ได้ทั้งพื้นและอาคาร
  - ทยอยทำหลังธง `?render=gl` ได้ ผู้เล่นทั่วไปยังอยู่บน 2D จนกว่าจะผ่านเกณฑ์
  - ทำงานได้ทั้ง 4 โซนตั้งแต่แรก (โซน 2–4 ที่ยังใช้แผนที่แบบเก่าก็วาดผ่าน `drawImage` เหมือนกัน) ไม่ต้องรอพื้น HD
- **ข้อเสีย:**
  - เราต้องดูแลเองทั้งหมด: อายุ texture / หน่วยความจำ GPU, context หลุด, ความถูกต้องของ alpha, คุณภาพการย่อภาพ
  - canvas ลับที่เปลี่ยนทุกเฟรม (ชั้นเมฆ, ชั้นเงาตัวละคร, เฟรมของเหลว) ต้องส่งขึ้น GPU ทุกเฟรม — **ยังไม่ได้วัดว่าแพงแค่ไหน**
  - เฟสแรกจะยังไม่เร็วขึ้นอย่างเห็นได้ (9% ตาม prototype) ผลมาตอนรวมรอบในเฟสถัดไป
- **ขนาด:** เพิ่มโค้ดราว 50–80 KB ไม่บีบอัด (ประเมินจาก `fluid-shader.js` ที่ 25 KB) ไม่มีไลบรารีเพิ่ม
- **ความเสี่ยงเทสต์:** ต่ำ — โมดูลวาดคงหน้าตาเดิม เทสต์ `ctx` ปลอมยังใช้ได้ · ที่ต้องแก้ทุกเฟสคือเทสต์ regex ของเลข cache-bust ใน importmap (ราว 5–8 ไฟล์ต่อรอบ เหมือนงานก่อน ๆ) · ส่วน GPU ของตัววาดรันใน Node ไม่ได้ ต้องตรวจด้วยเบราว์เซอร์ (เครื่องมือเฟส 0)
- **Fallback:** ดีที่สุดในสามแบบ

## 3. แผนเป็นเฟส (ตัวเลือก ค)

ทุกเฟส deploy ได้: จนถึงเฟส 3 ค่าเริ่มต้นยังเป็น Canvas 2D เหมือนวันนี้ ตัววาดใหม่เปิดด้วย `?render=gl` เท่านั้น
เวลาเป็น **ค่าประเมิน** อิงจากงานก่อนหน้า (shader ของเหลวใช้ ~2 วัน) · หน่วย = วันทำงานของคนเขียนโค้ด 1 คน ไม่รวมรอบรีวิว
เกณฑ์ fps วัดด้วย harness `perf-1110` เดิม: หน้าต่าง 1792×958 DPR 2 · โหมดความละเอียดสูง · Intel UHD 630 · มัธยฐานอย่างน้อย 4 รอบ · load เครื่อง < 2.5
ค่าอ้างอิงวันนี้: ยืนนิ่ง 60 fps · เดินเมือง 45.7–52.6 fps (p95 33 ms)

## 4. ผลต่อส่วนอื่น

**ปุ่มกราฟิก (ความละเอียดสูง / เน้นประสิทธิภาพ)**
- อยู่ต่อจนจบเฟส 4 ไม่แตะ
- หลังเฟส 4 ถ้าโหมดความละเอียดสูงเดินเมืองได้ ≥ 59 fps ที่ DPR 2 → ถามคุณเป้ก่อนถอด (วิธีถอดเขียนไว้แล้วในงาน 10 พ.ย. ค้นคำว่า `GFX-1110`)
- ข้อสังเกต: เพดาน DPR 1.5 อาจยังมีประโยชน์กับมือถือ/เครื่องอ่อน แม้ถอดปุ่มออกจากหน้าตั้งค่า — เป็นเรื่องให้ตัดสิน

**Shader ของเหลวที่มีอยู่ (`fluid-shader.js`)**
- GLSL เดิมใช้ต่อได้ · ที่เปลี่ยนคือปลายทาง: วาดตรงลงเฟรมแผนที่ แทนการวาดลง canvas ลับแล้วคัดลอกกลับเข้า 2D (การคัดลอกนี้ตอนเดินกินอยู่ 1.6 MP ต่อเฟรม)
- ชั้นของเหลวแบบเฟรมวาดที่ยังเหลือ (ตอนเดิน ~3.8 MP ต่อเฟรม + งานใน canvas ลับ 1.9 MP) ไม่หายไปเอง — ในโหมด GL จะกลายเป็นสี่เหลี่ยมธรรมดา ยังต้องวาดอยู่
- ทางสำรอง `?fluid=frames` (เฟรมวาด) คงไว้สำหรับโหมด 2D
- ตัวหน่วงของเหลวในโหมดเน้นประสิทธิภาพจะหายไปพร้อมปุ่มกราฟิก

**แสง normal map**
- ทำบน Canvas 2D ไม่ได้ · ตัวเลือก ค ทำได้ทั้งพื้นและอาคารเพราะเป็นเจ้าของ shader ของ sprite เอง
- ไม่เริ่มจนกว่าเฟส 4 จบ ตามที่คุณเป้สั่งไว้
- ต้องมีอาร์ตเพิ่ม: normal map ต่ออาคาร (และพื้น ถ้าต้องการ) — ผมจะเขียนสเปก (ขนาด, ชื่อไฟล์, มุม) ก่อนให้ใครวาด

**มือถือ (Capacitor) / Steam (Tauri)**
- WebGL2 มีใน WKWebView (iOS/macOS), WebView2 (Windows), Android WebView — เป็นความรู้ทั่วไป **ผมไม่ได้ทดสอบบนเครื่องจริง**
- ข้อดีต่อมือถือ: โหมด GL ไม่ต้องเก็บ cache ชิ้นพื้นขนาดเท่าจอ (เพดานปัจจุบัน 72 MP ≈ 288 MB · รายงาน 10 พ.ย. ประเมินใช้จริง ~140 MB)
- ความเสี่ยง: มือถือทิ้ง context WebGL เมื่อแอปไปอยู่เบื้องหลัง → ตัววาดต้องสร้าง texture ใหม่ได้เองตั้งแต่เฟส 1 · Linux/Steam Deck (WebKitGTK) ยังไม่มีข้อมูล
- ถ้าหน่วยความจำ GPU บนมือถือไม่พอ มีทางเพิ่มภายหลังคือ texture แบบบีบอัด (KTX2) — ต้องเพิ่มขั้นตอนแปลงไฟล์ ยังไม่อยู่ในแผนนี้
- กติกา portrait 390×844: ตัววาดไม่ผูกกับขนาดจอ ใช้ `mapViewport` เดิม

**ขนาด deploy**
- ปัจจุบัน: `img` 669 MB · `audio` 7.9 MB · `src` 4.1 MB (เพดาน GitHub Pages 1 GB)
- ตัววาดใหม่เพิ่ม ~50–80 KB — ไม่มีนัยสำคัญ
- สิ่งที่จะดันเข้าใกล้เพดานคือ **อาร์ต** ไม่ใช่โค้ด: พื้น HD โซน 2–4 (โซน 1 ใช้ 25 MB) และ normal map ในอนาคต

## 5. เรื่องที่คุณเป้ต้องตัดสิน

1. **สถาปัตยกรรม** — ใช้ตัวเลือก ค (ตัววาด WebGL2 ของเราเอง ไม่ใช้ PixiJS) ตามที่แนะนำ หรืออยากได้ PixiJS
2. **เกณฑ์ "ภาพเหมือนเดิม"** — เข้มแค่ไหน:
   - (ก) ต่างได้ไม่เกินระดับที่ตาไม่เห็น เช่น เฉลี่ยไม่เกิน 2 จาก 255 — ทำได้ตามแผน
   - (ข) ต้องเท่ากันทุกพิกเซล — ทำได้ยากกว่ามาก เพราะ GPU ย่อภาพคนละสูตรกับ Canvas 2D และจะเสียประโยชน์ด้านหน่วยความจำ
3. **เก็บ Canvas 2D เป็นทางสำรองนานแค่ไหน** — เก็บไว้ = effect ใหม่ทุกตัวต้องทำงานได้สองทาง (หรือประกาศว่าเป็นของ GL เท่านั้น) · ข้อเสนอ: เก็บจนกว่าจะตัดสินเรื่องลง Steam
4. **ปุ่มกราฟิก** — หลังเฟส 4 ผ่านเกณฑ์ ถอดเลย, เก็บไว้, หรือถอดปุ่มแต่คงเพดาน DPR 1.5 ไว้ใช้กับมือถือ
5. **เครื่องอ้างอิง** — ตอนนี้วัดได้เครื่องเดียว (MacBook Intel UHD 630) · จะให้ถือเครื่องนี้เป็นเกณฑ์ หรือมีเครื่อง Windows / มือถือให้ทดสอบเพิ่มช่วงเฟส 4
6. **ชายแดน/ดันเจี้ยน (เฟส 5)** — ทำต่อเลย หรือรอวัดก่อนว่ากระตุกจริงไหม
7. **จังหวะ merge** — งานนี้ทำบน branch ที่จะ merge เมื่อพื้น HD ครบ 4 โซน · ตัววาด GL ไม่ต้องรอพื้น HD จึงเริ่มเฟส 0–1 ขนานกับงานวาดพื้นได้ ถ้าคุณเป้ต้องการ

## ความเสี่ยง

1. **ภาพไม่เหมือนเดิม** — การย่อภาพของ GPU (mipmap) คมไม่เท่า resample คุณภาพสูงของ Canvas 2D · ขอบ alpha · โปรไฟล์สี · ทางลด: เฟส 1 ส่ง canvas ที่ resample แล้วของเดิมขึ้นเป็น texture ตรง ๆ ก่อน แล้วค่อยเปลี่ยนเป็น mipmap เฉพาะจุดที่ตัวเทียบภาพผ่าน
2. **ตัวเลข 45% มาจากงานสังเคราะห์** — เกมจริงอาจได้น้อยกว่า ต้องวัดจริงตอนจบเฟส 2 · ถ้าไม่ถึงเกณฑ์ให้หยุดทบทวนก่อนทำเฟส 3
3. **ยังไม่ได้วัด 2 จุด** — ค่าใช้จ่ายของการส่ง canvas ลับขึ้น GPU ทุกเฟรม และของการส่ง path/ตัวหนังสือขึ้นตามลำดับ (~120 คำสั่งต่อเฟรม) · ทั้งสองจะรู้ในเฟส 1
4. **หน่วยความจำ GPU / context หลุด** — texture ชิ้นพื้น 1024 px = 4 MB ต่อชิ้น (+33% เมื่อมี mipmap) · ต้องมีการคืนหน่วยความจำและสร้างใหม่ได้
5. **ดูแลสองเส้นทาง** — ตราบที่ยังเก็บ 2D เป็นทางสำรอง
6. **เทสต์** — เทสต์ regex ของ importmap ต้องแก้ทุกเฟส · ส่วน GPU ทดสอบใน Node ไม่ได้ ต้องพึ่งการรันในเบราว์เซอร์
7. **วัดเครื่องเดียว** — MacBook เครื่องนี้ลดความเร็วเมื่อร้อน ตัวเลขแกว่งได้ ±7 fps (เจอตั้งแต่ 10 พ.ย.) · ไม่มีข้อมูล Windows / มือถือ / Linux
