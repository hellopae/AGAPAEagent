# ประเมินความเป็นจริง — "ทำเกมจริงขึ้นมาขาย"

**เขียนโดย:** Toby (gamedev) · 5 ก.ย. 2569
**โจทย์:** เจ้าของอยากต่อยอดจากผังออฟฟิศ interactive ไปเป็นเกมที่ขายได้
**กติกาที่ยึด:** พูดตามของที่มีจริงในโค้ด ไม่ใส่ตัวเลขตลาด/ยอดขาย (Reese ทำส่วนนั้น)

> สรุปหนึ่งบรรทัดก่อน: **ทำได้ ถ้าเลือกแนวที่ไม่ต้องมีท่าเดินตัวละคร และล็อกจำนวนรูปตั้งแต่วันแรก**
> คอขวดของโปรเจกต์นี้คือ "งานวาด" ไม่ใช่ "งานโค้ด" — และเรามีหลักฐานเรื่องนี้อยู่ในเครื่องแล้ว

## 1. ของที่มีอยู่จริง พาเราไปได้แค่ไหน

### 1.1 สิ่งที่ต้องเข้าใจก่อน — เราไม่ได้มี "เอนจิน" หนึ่งตัว เรามีของสองอย่างที่ไม่เกี่ยวกัน

| ระบบ | เทคโนโลยีจริง | ไฟล์ |
|---|---|---|
| ผังออฟฟิศ | **DOM** — `<div>` ขยับด้วย `style.left/top` เป็น % | `index.html` (`ofcTick`) |
| มินิเกม 8 เกม | **canvas 2D** เขียนมือล้วน | `games.js` (`gmCanvas`, `gmLoop`) |

สองอย่างนี้แชร์กันแค่ "รูปสไปรท์" กับ "Firestore" เท่านั้น ไม่ได้แชร์โค้ดเลย
เวลาพูดว่า "เอนจินที่เรามี" ต้องแยกให้ออก ไม่งั้นจะประเมินสูงเกินจริง

### 1.2 ระบบเดิน/collision/pathfinding — ดีสำหรับ "ผังเดียว" ไม่ใช่สำหรับ "เกม"

- `ofcRoute(from,to)` ใน `index.html:3056` = **BFS บนกราฟ 24 จุดที่พิมพ์มือ** (`OFC_NODES` / `OFC_EDGES`)
  ทุกพิกัดวัดจากรูป `office/floor2.2.png` ทีละจุดด้วยตา — ไม่ใช่ tilemap ไม่ใช่ A* ไม่มี grid
- `ofcWalkable(x,y)` ใน `office-live.js:251` = กรอบห้องหดเข้า 12 หน่วย + แถบกว้าง 34 หน่วยตามเส้น `OFC_EDGES` + ช่องประตู
  ในโค้ดเขียนไว้ตรงๆ ว่า *"ผังเป็นรูปเดียว ไม่มีข้อมูล collision จึงประกอบเอาจากของที่มีอยู่แล้ว"*
- ชนกำแพงแล้วไถลไปตามแกน (แยกแกน x/y) — พอใช้ แต่เป็นของทำมือสำหรับแผนที่ใบเดียว

**แปลว่า:** ถ้าเกมมี 5 ฉาก = ต้องนั่งวัดพิกัดมือใหม่ 5 รอบ ไม่มีเครื่องมือช่วย
ระบบนี้ **ไม่ scale** ไปเกมที่มีหลายแผนที่ ถ้าจะไปทางนั้นต้องใช้ Tiled + engine ที่โหลด tilemap ได้

### 1.3 สไปรท์ — จุดที่เราเคยแพ้มาแล้วหนึ่งครั้ง

- ท่ายืน/ท่านั่ง gen มาแล้วปรับด้วย `scripts/make-sprites.py` (ครอปขอบใส · ย่อสูง 512px · ลด palette 96 สี)
  และ `scripts/fit-sit-sprite.py` (แก้ตัวลอยเหนือพื้น)
- **แต่ท่าเดินถูกปิดอยู่** — `const OFC_WALK = {}` (`index.html:2822`) คอมเมนต์ในโค้ดบอกเหตุผลตรงๆ:
  *"ชีตแต่ละคนสเกล/ทิศทาง/ระยะขอบเฟรมไม่ตรงกัน ทำให้บางคนเดินถอยหลัง บางคนตัวใหญ่กว่าเพื่อน"*
  ไฟล์ `office/sprites/*-W.png` มีครบทุกคน แต่ใช้ไม่ได้

นี่คือข้อมูลที่สำคัญที่สุดในเอกสารนี้ — **เรายังไม่มี pipeline ทำอนิเมชันตัวละครที่ใช้งานได้จริง**
เราลองแล้ว เขียนสคริปต์ Python มาสู้แล้วสองตัว และยังต้องปิดทิ้ง
เกมไหนที่ต้องมีตัวละครเดิน/ตี/โดนตี = ไปเจอกำแพงนี้ตั้งแต่วันแรก และรอบนี้ปิดทิ้งไม่ได้เพราะมันคือตัวเกม

### 1.4 ของที่ "ไม่มีเลย" (เช็คจากโค้ดแล้ว ไม่ใช่เดา)

- **เสียง — ศูนย์** `grep` หา `new Audio` / `AudioContext` / `.mp3` / `.wav` ใน `games.js` + `index.html` + `office-live.js` = ไม่เจอสักที่
  เกมขายที่ไม่มีเสียงไม่มีอยู่จริง และเราไม่เคยเขียนระบบเสียงมาก่อนเลยสักบรรทัด
- **ไม่มี sprite atlas / texture packer** — `office/` หนัก **34MB**, `avatars/` **28MB**, PNG รายไฟล์ 100KB–1.2MB
- **ไม่มี build step, ไม่มี module, ไม่มี test** — ฟังก์ชัน global ล้วน, `index.html` 4,358 บรรทัด / 265KB
  (ข้อดีคือแก้แล้วรีเฟรชเห็นเลย ซึ่งเป็นสาเหตุที่เราทำงานเร็ว — แต่ยืดไปเกมที่ดูแล 6 เดือนไม่ไหว)
- **ไม่มีระบบเซฟที่ปลอดภัย** — `gmSave()` เขียน localStorage + Firestore `agents/games`
  ซึ่ง PHASE2-GAMES.md เตือนเองว่า *"อ่านได้ด้วย API key ที่ฝังในหน้าเว็บสาธารณะ"* → ใครก็แก้สถิติได้

### 1.5 แล้วเราทำอะไรได้จริง

**ทำได้ (มีหลักฐานว่าทำแล้ว):**
- เกมจอเดียว/ไม่กี่จอ 2D: จับจังหวะ, พัซเซิล, tycoon เบาๆ, เลี้ยงสัตว์, ลาก-วางตกแต่ง, เทิร์นเบส
- ความเร็วจริงที่วัดได้: **มินิเกม 8 เกม + กระดานแชมป์ เสร็จใน git log ราว 3 คืน (26 ส.ค.)**
  และ `Cat in Room` (เกมเลี้ยงแมว, `game.js` 497 บรรทัด) core loop เสร็จใน 2 เซสชัน
- ระบบเดิน/ชน/กดของ ในผังเดียว เสร็จใน 2 วัน (4–5 ก.ย.)

**ก้ำกึ่ง (ทำได้แต่ต้องแก้ของที่พังก่อน):**
- เกมที่ตัวละครต้องเดินมีท่า → ต้องรื้อ pipeline สไปรท์ใหม่ทั้งหมดก่อน
- เกมที่มีเนื้อเรื่องยาว → ไม่ใช่ปัญหาโค้ด แต่เป็นปริมาณงานเขียน (Rae) + งานวาด

**ทำไม่ไหว — พูดตรงๆ:**
- **3D** — `RushExit` มี `three.min.js` จริง แต่เป็นพัซเซิลกล่องเลื่อน ไม่มีโมเดล ไม่มี rig
  เกม 3D จริงต้องมีคนปั้นโมเดล + rig + animate = งานเต็มเวลาของอีกคนหนึ่ง
- **มัลติเพลเยอร์เรียลไทม์** — netcode + เซิร์ฟเวอร์ + กันโกง + ค่ารันรายเดือน คนเดียวไม่จบ
- **โลกกว้าง/หลายสิบแผนที่** — ระบบพิกัดมือของเราตายตั้งแต่แผนที่ที่ 3
- **เกมที่ต้องใช้ศิลปินเต็มเวลา** (ประมาณ 200+ asset มีอนิเมชัน) — เจ้าของบริหารโรงพิมพ์อยู่ ไม่มีเวลานั้น
- **พอร์ตลงคอนโซล** — ไม่ต้องคิดถึงในรอบนี้

## 2. เทียบ 4 แนวที่เจ้าของยกมา

> หน่วย "สัปดาห์-คน" ในที่นี้ = สัปดาห์ของคนที่มีงานประจำอยู่แล้ว (~15–20 ชม./สัปดาห์) + Claude ช่วยเขียน
> "prototype" = เล่นได้ ตัดสินได้ว่าสนุกไหม · "ชิปได้" = มีอาร์ตจริง มีเสียง มีสอนเล่น มีจุดจบ

### A. ร้านอาหารไทย (time management)
**ต้องเขียน:** คิวออเดอร์ · ตัวจับเวลาต่อสถานี · สเตตแมชชีนการปรุง · มาตรความอดทนลูกค้า · เงิน/อัปเกรด · ลูปกะ/วัน · ปลดเมนู · ข้อมูลเลเวล · สอนเล่น · จูนความยาก
**ของที่ใช้ซ้ำได้:** `gmCoffee()` (`games.js:1387`) **คือเกมนี้เวอร์ชันสถานีเดียวอยู่แล้ว** — มีทั้งแถบรินที่ต้องหยุดให้ตรง (`S.lo/S.hi` แคบลงเรื่อยๆ ตามแก้วที่ผ่านไป), ออเดอร์ส่วนผสมเทียบกับที่ใส่จริง (`S.need` vs `S.add`), ให้ดาว 1–5 (`rate()`), และคำติชมแยกตามดาว
**อาร์ต:** ภาพนิ่งล้วน — ลูกค้าโผล่ที่โต๊ะได้ **ไม่ต้องมีท่าเดิน** ← เลี่ยงกับดักข้อ 1.3 ได้พอดี
**หนักตรงไหน:** จูนสมดุลเศรษฐกิจ + ปริมาณข้อมูลเลเวล (แต่ละด่านต้องนั่งจูนมือ)
**ประเมิน:** prototype **1.5–2 สัปดาห์** · ชิปได้ **5–7 สัปดาห์** (โค้ด) โดยงานวาดเดินขนานไป

### B. ท่องเที่ยวไทย
**ต้องเขียน:** แผนที่แบบจุดต่อจุด · ฐานข้อมูลสถานที่ · สมุดสะสม/อัลบั้ม · มินิเกมประจำจุด · ระบบปลดล็อก
**ของที่ใช้ซ้ำได้:** โมเดลกราฟ `OFC_NODES`/`ofcRoute` เข้ากับ "แผนที่เดินทาง" ได้ดี แต่โค้ดอื่นแทบไม่ได้ใช้ซ้ำ
**หนักตรงไหน:** **เนื้อหา ไม่ใช่โค้ด** — 20 จุดหมาย = 20 ภาพประกอบ + ข้อความที่ต้องหาข้อมูลจริง + กลไกต่อจุด
ถ้าไม่มีกลไกต่อจุด มันจะกลายเป็นสไลด์โชว์สวยๆ ที่ไม่ใช่เกม
เพิ่มอีกสองข้อ: ข้อมูลสถานที่จริง = ต้องผ่าน fact-check ทุกบรรทัด และถ้าใช้ภาพถ่ายต้องเคลียร์สิทธิ์
(MyTrips เจอเรื่องนี้มาแล้ว — ต้องใช้ URL thumb ที่ Wikimedia คืนมาตรงๆ)
**ประเมิน:** prototype **2 สัปดาห์** · ชิปได้ **8–12 สัปดาห์** และเป็นแนวที่เสี่ยง "สวยแต่ไม่ใช่เกม" ที่สุด

### C. ตกแต่งบ้านไทย (dollhouse / decoration)
**ต้องเขียน:** ลาก-วางพร้อม snap · จัดชั้นความลึก · แคตตาล็อก/คลังของ · เซฟผัง · เลื่อน/ซูมกล้อง · ปลดล็อกของ · แคปหน้าจอแชร์
**ของที่ใช้ซ้ำได้:** `ofcBuildProps()` วางของในผังอยู่แล้ว · ทริกความลึกใช้ `zIndex = Math.round(y)` ตรงๆ ใน `ofcTick()`
· และ `Cat in Room/ASSET-PROMPTS.md` **คือสเปกอาร์ตของแนวนี้ที่เขียนเสร็จแล้ว** (front elevation, แสงบนซ้าย, พื้นหลังใส, 1 ชิ้น/1 ภาพ, 1024×1024)
**เบาที่สุดในสี่แนว** — ไม่มี AI ไม่มีตัวจับเวลา ไม่มีสมดุลให้จูน
**หนักตรงไหน:** มันยังไม่ใช่ "เกม" จนกว่าจะมีเป้าหมาย — ต้องมีระบบโจทย์ ("จัดห้องให้ลูกค้าคนนี้") + เกณฑ์ให้คะแนน
ตรงนี้คืองานออกแบบจริงที่ต้องให้ Vera คิด ไม่ใช่งานโค้ด
อาร์ตเยอะที่สุดต่อความสนุกหนึ่งหน่วย — **แต่เป็นอาร์ตชนิดที่ถูกที่สุดที่เรารู้วิธีผลิต** (PNG นิ่งชิ้นเดียว)
และเฟอร์นิเจอร์ไทยวาดมือคือของที่ก๊อปไม่ได้จริงๆ
**ประเมิน:** prototype **1–1.5 สัปดาห์** · ชิปได้ **4–6 สัปดาห์** (โค้ด) อาร์ตทยอยเพิ่มได้เรื่อยๆ

### D. ผจญภัย
**ต้องเขียน:** อนิเมชันตัวละคร (เดิน/ตี/โดน/ตาย × ทิศทาง) · ระบบต่อสู้ · AI ศัตรู · หลายแผนที่พร้อม collision รายฉาก · ศัตรูหลายชนิด · ระบบพัฒนาตัวละคร · เซฟที่มี state เยอะกว่าเดิมมาก · บอส · เสียงที่มีผลต่อความรู้สึกมากที่สุดในบรรดา 4 แนว
**ของที่ใช้ซ้ำได้:** **แทบไม่มี** — ระบบพิกัดมือ + กรอบสี่เหลี่ยมของเราไม่รองรับ ต้องเปลี่ยนไปใช้ Tiled + engine จริง
และข้อแรกในลิสต์คือสิ่งที่เราปิดทิ้งไปแล้วเพราะทำไม่สำเร็จ (`OFC_WALK = {}`)
**ประเมิน:** **6 เดือนขึ้นไป** และเป็นแนวที่มีโอกาสถูกทิ้งกลางทางสูงที่สุด
**ข้อเสนอของผม: ยังไม่ทำ** ไม่ใช่เพราะไม่เก่งพอ แต่เพราะปริมาณอาร์ตกับเวลาที่มีไม่ตรงกัน

## 3. ทางเลือกเทคโนโลยี

### (ก) เขียน canvas เองต่อแบบเดิม + GitHub Pages
- **ดี:** ไม่มี build ให้รอ · แก้แล้วรีเฟรชเห็นทันที · เร็วจริง (พิสูจน์แล้ว 8 เกม/3 คืน) · เราเป็นเจ้าของทุกบรรทัด · ไม่ต้องเรียนของใหม่
- **เสีย:** ต้องเขียนเองทุกอย่างที่เอนจินแจกฟรี — atlas, อนิเมชัน, เสียง, tween, particle, scene, physics
  · ไม่มี editor · เซฟได้แค่ localStorage/Firestore · ไม่มี crash report
- **สรุป:** โอเคสำหรับเกมจอเดียวเล็กๆ แต่พอเริ่มมีอนิเมชันกับเสียงจะกลายเป็นการเขียนเอนจินเองโดยไม่ได้ตั้งใจ

### (ข) Phaser 3 — **ที่ผมแนะนำ**
- **ดี:** ยังเป็น JS/เว็บ วิธีคิดเดิมทั้งหมด · แจกของที่เราขาดพอดี: sprite atlas + animation manager
  (**คือของที่แก้ปัญหา `OFC_WALK` โดยตรง**), audio manager, tween, arcade physics, โหลด tilemap จาก Tiled, scene manager
  · เกมเราเกมละ 100–300 บรรทัด ย้ายแล้วโค้ดสั้นลง ไม่ยาวขึ้น · Claude เขียน Phaser ได้แม่นเพราะเป็น JS ธรรมดา
- **เสีย:** ต้องเรียน API ใหม่ (สะดุดราวหนึ่งสัปดาห์) · ไฟล์หนักขึ้น · ยังเป็นเว็บ ถ้าจะลงเดสก์ท็อปต้องห่อด้วย Tauri/Electron
- **สรุป:** **คุ้มที่สุดสำหรับแนว A และ C** ได้ของที่เราขาดมากที่สุด (อนิเมชัน + เสียง) โดยไม่ทิ้งภาษาที่ถนัด

### (ค) Godot 4
- **ดี:** เอนจินเต็มตัว มี editor, AnimationPlayer, เสียง, physics · export ได้ทั้ง Windows/Mac/Linux/Android/iOS/Web · ฟรี ไม่มีค่า royalty · เป็นทางที่ถูกต้องถ้าปลายทางคือ Steam จริงจัง
- **เสีย:** GDScript = ภาษาใหม่ · **Claude เขียน GDScript ได้แม่นน้อยกว่า JS** · โค้ดเดิมทิ้งทั้งหมด
  · ไฟล์ `.tscn`/ซีนไม่ได้อยู่ในรูปข้อความที่ AI แก้ได้สะดวก — งานส่วนใหญ่ย้ายไปอยู่ใน editor ที่ Claude แตะไม่ถึง
  สำหรับคนที่ leverage ทั้งหมดคือ "AI เขียนโค้ดให้" ข้อนี้ไม่ใช่เรื่องเล็ก
- **สรุป:** เลือกก็ต่อเมื่อยอมทำเกมใหญ่ (ผจญภัย) หรือ Steam-first — ซึ่งรอบนี้ผมแนะนำว่ายัง

### (ง) Unity
- ไม่แนะนำ: ใหญ่เกินความจำเป็น · เงื่อนไขไลเซนส์ยุ่ง · C# + editor workflow เข้ากับ AI-assist ได้แย่ที่สุดในสี่ตัว · ช้าที่สุดกว่าจะได้ของที่เล่นได้

### ช่องทางขาย — ตรงไปตรงมา

  แต่ **ไม่มีระบบเก็บเงินในตัว** ถ้าจะขายต้องสร้าง paywall/license server เอง ซึ่งเราไม่ควรทำ

  → **เป็นทาง "ขายจริง" ที่ใกล้ที่สุดจากจุดที่เรายืนอยู่** ไม่ต้องสร้างระบบอะไรเพิ่มเลย
- **Steam** — ต้องมี: ค่าธรรมเนียมเปิดเกมครั้งเดียวต่อเกม, ไฟล์เดสก์ท็อป, หน้าร้าน (capsule art + ตัวอย่างวิดีโอ), ผ่านรีวิว

  ข่าวจริง: งานที่ "ไม่ใช่การเขียนเกม" (หน้าร้าน อาร์ตปก ตัวอย่างวิดีโอ เซ็นไฟล์) กินอีกราว 2–3 สัปดาห์
  และคนบน Steam เทียบเกมเรากับเกมที่ขัดมาแล้วเป็นปี — **อย่าเริ่มที่นี่**
- **มือถือ (Capacitor)** — ค่าโปรแกรมนักพัฒนารายปีของ Apple + รีวิว + ไอคอน/สกรีนช็อต/แบบฟอร์มความเป็นส่วนตัว
  Android ง่ายกว่ามาก → ค่อยทำหลังจากเวอร์ชันเว็บพิสูจน์แล้วว่ามีคนเล่น

## 4. สิ่งที่จะฆ่าโปรเจกต์นี้

เรียงตามความน่าจะเป็น จากกับดักที่เจอมาแล้วจริง + ธรรมชาติของงานเกม

1. **สไปรท์ไม่เท่ากัน — เคยฆ่าท่าเดินมาแล้วหนึ่งรอบ**
   `OFC_WALK = {}` คือหลุมศพจริงในโค้ดเรา รูปที่ gen มาไม่เคยได้สเกล/ทิศ/ขอบเฟรมเท่ากันเลย
   เราเขียนสคริปต์ Python มาสู้สองตัวแล้วยังต้องปิดทิ้ง
   **ทางกัน:** ล็อกสเปกอาร์ตก่อนวาดเสมอ (ขนาด/จำนวนเฟรม/กรอบเฟรมตายตัว/มุมมอง/ชื่อไฟล์) · ใช้ atlas ·
   และวิธีที่ปลอดภัยที่สุดคือ **เลือกแนวที่ต้องการท่าทางน้อยที่สุด**

2. **ปริมาณงานวาด ไม่ใช่ปริมาณโค้ด — มีหลักฐานอยู่ในเครื่องแล้ว**
   `Cat in Room` core loop เสร็จ 15 ส.ค. · แก้ลูปเป็นเลี้ยงแมว 24 ส.ค. · **แล้วนิ่งมาตั้งแต่นั้น**
   README เขียนเองว่า *"ท่าแมวมีแค่ท่า idle 3 เฟรม · ของในห้องยังเป็นกล่อง placeholder รอรูปวาด"*
   เกมไม่ได้ตายเพราะโค้ดไม่เสร็จ มันตายตรงที่รอรูป
   **ทางกัน:** นับจำนวนรูปที่เวอร์ชันขายต้องมี **ให้จบก่อนเขียนโค้ดบรรทัดแรก** แล้วตั้งเพดานไว้ ห้ามเกิน

3. **ตรรกะชุดเดียวกันอยู่สองที่แล้วเพี้ยน** — โดนมาแล้วอย่างน้อยสามครั้ง
   (สูตรเลเวล `index.html` vs `Widget/src/levels.js` · PrintCost สองไฟล์ · budget2569 สองที่)
   ในเกมมันจะโผล่มาเป็น "ค่าความยากอยู่ทั้งในโค้ดและในไฟล์ด่าน"
   **ทางกัน:** ข้อมูลสมดุลอยู่ใน JSON ไฟล์เดียว โค้ดอ่านอย่างเดียว ห้ามมีค่าคงที่ซ้ำที่สอง

4. **Firestore ที่ใครก็เขียนได้** — PHASE2-GAMES.md เตือนเองว่า `agents/games` เปิดด้วย API key ที่ฝังในหน้าเว็บ
   เกมที่ขายแล้วมีกระดานคะแนนใช้รูปนี้ไม่ได้ **ทางกัน:** v1 เก็บ localStorage อย่างเดียว หรือยอมรับว่ากระดานเป็นแค่ของประดับ

5. **ขยายสโคปโดยเรียกมันว่า "ฟีเจอร์"** — เราทำ 8 เกมได้ใน 3 คืนเพราะแต่ละเกมเล็ก
   พลังงานเท่ากันเทลงเกมเดียว = ได้เกมใหญ่ที่สร้างค้างครึ่งทาง
   สังเกตของจริง: PHASE2-GAMES.md เพิ่ม "เฟส 3" (TTL/ใบลา/บทพูดลับ) เข้ามาแล้ว **ทั้งที่รอบ 4 ยังไม่เสร็จ**
   (กระดานโยนงานยังไม่ได้ทำ) — พฤติกรรมแบบนี้ในเกมที่ต้องขาย = จบเห่

6. **ไม่มีเสียงเลยสักบรรทัด** เพิ่งจะไปเจอครั้งแรกตอนทำเกมขาย: นโยบาย autoplay บนมือถือ ต้องรอ user gesture,
   ฟอร์แมตไฟล์, และหาเสียง/เคลียร์สิทธิ์ **ทางกัน:** กันเวลาไว้เป็นฟีเจอร์เต็มหนึ่งรอบ อย่าคิดว่าเป็นงานขัดเงา

7. **ไฟล์อาร์ตหนัก** — 34MB ในโฟลเดอร์เดียว, PNG ละ 400KB–1.2MB, ยังไม่เคยทำ atlas เลย
   เกมเว็บที่โหลด 30 วินาทีคือเกมที่ไม่มีใครได้เล่น

8. **ไม่มีใคร QA เกมได้นอกจากเป้** — Chris ตั้งมาสำหรับงานเขียน/งานพิมพ์ ไม่ใช่เกม
   เกมพังบน iOS Safari (ทัช/viewport/เสียง) จะไม่มีใครเจอ
   กฎข้อแรกของผมที่ว่า "ห้ามบอกว่าเสร็จถ้ายังไม่ได้รันเอง" มีอยู่เพราะเรื่องนี้เคยเป็นปัญหาจริง

9. **ภาษาไทยกับการแปล** — ถ้าวันหนึ่งขายนอกไทย ทุกข้อความต้องอยู่ในตารางข้อความตั้งแต่วันแรก
   ทำตอนนี้ = ฟรี · ทำทีหลัง = รื้อทั้งเกม

## 5. ข้อเสนอ scope ที่ทำเสร็จได้จริงใน 4–6 สัปดาห์

### เลือกอะไร: **เกมร้านอาหารไทย แบบจับเวลา จอแนวตั้ง**

เหตุผลที่เลือกแนวนี้ ไม่ใช่เพราะสนุกที่สุด แต่เพราะ **จบได้จริงที่สุด**:
1. `gmCoffee()` คือ vertical slice ของกลไกนี้ที่ **เราเขียนเองและมันทำงานอยู่แล้ว** — ไม่ต้องเดาว่าทำได้ไหม
2. ใช้ภาพนิ่งล้วน ลูกค้านั่งโต๊ะ ไม่ต้องเดิน → **หลบกับดักอนิเมชันที่เคยฆ่าเรามาแล้ว**
3. เข้ากับจอแนวตั้ง 390×844 พอดี (กฎข้อ 1 ของผม)
4. อาหารไทยวาดมือ = จุดต่างที่เอนจินไหนก็ซื้อไม่ได้
5. มีจุดจบชัดเจน ("ครบ 10 ด่าน") → **ปิดกล่องได้** ต่างจากแนวตกแต่งที่ไม่มีเส้นชัยตามธรรมชาติ

> ถ้าเจ้าของอยากได้แนวตกแต่งมากกว่า ก็ทำได้และโค้ดเบากว่าด้วย — แต่ต้องให้ Vera ออกแบบ
> "ระบบโจทย์ + เกณฑ์คะแนน" ให้เสร็จก่อน ไม่งั้นได้ของเล่นที่ไม่ใช่เกม

### Milestone (หนึ่งรอบ = หนึ่งฟีเจอร์ ส่งให้เป้ลองทุกรอบ)

**สัปดาห์ 0 — 2-3 วัน ตัดสินใจก่อนแตะโค้ด**
- Vera เขียนสเปก core loop: 1 จาน → ออเดอร์ → ปรุง → เสิร์ฟ → ให้คะแนน
- **นับรายการอาร์ตให้ครบและตั้งเพดาน** (ตัวเลขจริง เช่น 8 จาน + 6 ลูกค้า + 1 ฉากครัว + UI)
- repo ใหม่ Vite + Phaser 3 + TS, ล็อก 390×844
- *ส่งมอบ:* สเปก + รายการอาร์ตที่ปิดแล้ว + repo เปล่าที่ build ผ่าน

**สัปดาห์ 1 — vertical slice จานเดียว**
- 1 จาน 1 ลูกค้า ครบลูป ให้ดาว · อาร์ตยังเป็นกล่อง+ชิบิที่ gen ไว้แล้ว
- ต้องเล่นบนมือถือเป้ได้จริง
- **ประตูตัดสิน: ถ้าจานเดียวยังไม่สนุก สิบจานก็ไม่สนุก — หยุดหรือรื้อแบบตรงนี้ อย่าเดินต่อ**

**สัปดาห์ 2 — วันทำการ + เศรษฐกิจ**
- นาฬิกากะ, 3–5 จาน, มาตรความอดทน, เงิน, สรุปท้ายวัน, เซฟ localStorage
- ค่าความยากทั้งหมดอยู่ใน JSON ไฟล์เดียว (ดูกับดักข้อ 3)

**สัปดาห์ 3 — เสียง + ความรู้สึกมือ**
- ระบบเสียงครั้งแรกของทีม (ถือเป็นฟีเจอร์เต็ม ไม่ใช่งานขัดเงา)
- tween/particle/สั่นจอเบาๆ · สอนเล่น 60 วินาทีแรก · ทำ atlas + วัดเวลาโหลด

**สัปดาห์ 4 — เอาอาร์ตจริงเข้าแทน placeholder**
- สลับรูปวาดมือของเป้เข้ามาตาม convention ชื่อไฟล์ที่ล็อกไว้ตั้งแต่สัปดาห์ 0 — **โค้ดไม่ต้องแก้สักบรรทัด**
- ถ้ารูปยังไม่พร้อม ก็ปล่อยด้วยชุด placeholder ไปก่อนแล้วสลับทีหลังได้ เพราะ convention รองรับไว้แล้ว

**สัปดาห์ 5 — ปิดกล่อง**
- ข้อมูล 10 ด่านที่จูนมือแล้ว · หน้าจบเกม · ไล่บั๊กบน iOS Safari และที่ความกว้าง 360px
- ทำหน้า itch.io + อัปไฟล์ · อัดคลิป 30 วินาทีไว้แชร์

**สัปดาห์ 6 — สัปดาห์กันชน**
- สัปดาห์นี้จะหายไปเสมอ **ห้ามวางแผนงานลงไป**

### สิ่งที่ v1 จะ "ไม่ทำ" — ประกาศไว้ตั้งแต่ต้น
มัลติเพลเยอร์ · กระดานคะแนนออนไลน์ · Firestore · Steam · สโตร์มือถือ · โหมดเนื้อเรื่อง · ร้านที่สอง
หลังปล่อยแล้ว งานถัดไปคือ **การกระจายให้คนรู้จัก ไม่ใช่ฟีเจอร์เพิ่ม** (กฎข้อ 3 ของผม)

### ของแถมที่อาจต่อยอดได้ (ยังไม่นับใน scope)
ถ้าเป้อยากให้เกมช่วยธุรกิจโรงพิมพ์ด้วย แนวตกแต่งมีมุมที่เอนจินไหนก็ให้ไม่ได้ —
**เล่นจบแล้วสั่งพิมพ์ห้องที่จัดเองเป็นโปสเตอร์จากโรงพิมพ์ตัวเอง**
ยังไม่ต้องคิดตอนนี้ แต่จดไว้ก่อนจะลืม
