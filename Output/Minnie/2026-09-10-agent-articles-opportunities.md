## 0. จุดยืนที่คุณเป้ยืนได้แบบไม่ต้องขายฝัน (อ่านแค่นี้ก็เข้าใจทั้งไฟล์)

เคส "27 agent" ที่กำลังดังไม่ใช่ engineering case study — Reese ยืนยันว่ามันคือ **หน้าร้านของ blueprint ราคา $497–$4,997**
และเลขจำนวน agent ของเจ้าตัวเองขยับ 27 → 35 → "30+" → "100+" ใน 4 เดือน
แปลว่า **"มี agent กี่ตัว" ไม่ใช่หน่วยวัด มันคือชื่อสินค้า** — ใครก็พูดได้ ตรวจไม่ได้

ของที่ AGAPAE มีและเคสนั้นไม่มีเลยคือ **หลักฐานที่คนนอกเปิดดูได้**: dashboard สาธารณะ, worklog 189 entries,
ไฟล์ผลงาน 119 ชิ้นใน git ที่มี timestamp — และวันนี้เพิ่มมาอีกหนึ่งอย่างที่มีค่ากว่าความสำเร็จ:
**Dale จับได้ว่ากลไก enforcement ที่เอกสารเราโฆษณาว่า "บังคับด้วยโค้ด" ตายเงียบมาตั้งแต่ 29 ก.ค. — 6 สัปดาห์ ผ่านงานไปราว 50 entries**

**คำตอบข้อที่โจทย์ถาม: ใช่ — เรื่อง "ระบบพังแบบเงียบแล้วจับได้ยังไง" มีค่ากับคนเรียนมากกว่าเรื่องความสำเร็จ**
เหตุผล 3 ข้อ ไม่ใช่เพราะฟังดูถ่อมตัว:
1. **ตรวจได้** — มี mtime ของไฟล์ state, มี worklog, มี commit ให้เทียบ ต่างจากตัวเลข self-report ที่ยืนยันไม่ได้แม้ตัวเดียว
2. **เป็นปัญหาที่ผู้เรียนจะเจอแน่ ๆ** — คนติดตั้งชุด agent แล้วปล่อยทิ้ง 2 เดือนคือกรณีปกติ ไม่ใช่กรณีพิเศษ
3. **ลอกไม่ได้** — คู่แข่งลอกจำนวน agent ได้ในหนึ่งบ่าย แต่ลอก "เคสที่ตัวเองพังแล้วเล่าพร้อมหลักฐาน" ไม่ได้

⚠️ กติกาที่ทุกไอเดียข้างล่างต้องเคารพ: ตัวเลขของเคส 27 agent ทุกตัวเป็น **คำบอกเล่าใน as-told-to essay**

## ทิศทาง 1 — ใช้เป็นเนื้อหาคอร์ส/คอนเทนต์

### Idea 1.1 — โมดูลเสริม Course Agent: "จับระบบที่ตายเงียบ"

- **คอนเซปต์:** 1 บทเรียน + 1 ไฟล์ที่ผู้เรียนวางลงชุดตัวเองได้ทันที — log 1 บรรทัดต่อการยิง hook
  + วิธีดู "ตัวตรวจของฉันยังหายใจอยู่ไหม" ใน 10 วินาที เล่าจากเคสจริงของ AGAPAE พร้อมวันที่และชื่อไฟล์
- **ทำเพื่อใคร:** ลูกค้า Course Agent แพ็ก 2,900 / 8,900 ที่ติดตั้งชุด agent แล้วปล่อยทิ้ง —
  คนกลุ่มนี้จ่ายเพื่อ "ให้มันทำงานต่อเนื่อง" ไม่ใช่เพื่อ "ให้มันเดินได้วันแรก"
- **Hypothesis (ทดสอบได้):** บทเรียนที่บอกวิธีจับความพังจะถูกอ้างถึงในรีวิว/คำถามหลังเรียนมากกว่าบทเรียนวิธีสร้าง
  → วัดจากจำนวนคำถามหลังการขาย 10 รายแรกที่พูดถึง "ไม่แน่ใจว่ามันยังทำงานอยู่ไหม"
- **ทำไมตอนนี้:** เคสสด ๆ ของเราเอง + Dale ข้อเสนอ #1 **(ถ้า Kittanate อนุมัติ P0)** จะสร้าง `.hook-log.jsonl` อยู่แล้ว
  → โมดูลนี้เกิดจากงานที่จะทำอยู่ดี ไม่ต้องลงทุนซ้ำ
- **Effort:** 4–6 ชม. (Rae เขียน 1 บท + ตัวอย่าง 1 ไฟล์) — **ต้องรอ Dale #1 เสร็จก่อน**
- **เหตุผลที่อาจล้มเหลว:** ลูกค้าระดับ "ไม่เคยเปิด Terminal" ยังไม่เจอปัญหานี้ เขาอยากได้ agent ที่ใช้ได้ก่อน
  → ขายเป็นโมดูลแยกน่าจะไม่ขึ้น ควรแถมในแพ็กบนเป็น "ของที่ทำให้คุณไม่ถูกทิ้งไว้คนเดียว"
- **Research questions:** ผู้เรียนที่ผ่านมาถามอะไรบ้างหลังส่งมอบ 2–4 สัปดาห์? · คอร์ส agent ไทยเจ้าอื่นมีบทเรียนแนวนี้ไหม?
- **Format hint:** 1 หน้าในเว็บคอร์ส (`_site/build.py` GROUPS) + 1 ไฟล์ใน `kit/`

### Idea 1.2 — คอนเทนต์: "เช็คลิสต์ 5 ข้อ ก่อนจ่ายเงินซื้อคอร์ส AI Agent"

- **คอนเซปต์:** ไม่ใช่บทความตีเคสใคร แต่เป็น **เช็คลิสต์ที่ผู้อ่านเอาไปใช้กับคอร์สไหนก็ได้ (รวมคอร์สของเราเอง)**
  5 ข้อที่มาจากของที่ Reese ตรวจจริง: (1) ตัวเลขในเคสมาจากไหน — self-report หรือมีหลักฐานนอก
  (2) จำนวน agent เปลี่ยนไหมเมื่อเวลาผ่าน (3) มีของสาธารณะให้ดูไหม หรือมีแต่ของที่ต้องซื้อ
  (4) ภาพประกอบตรงกับเนื้อหาไหม (5) เจ้าของเคสยังทำธุรกิจนั้นอยู่ หรือย้ายมาขายวิธีทำ
- **ทำเพื่อใคร:** คนไทยที่กำลังจะจ่ายเงินซื้อคอร์ส/เทมเพลต agent — audience เดียวกับลูกค้า Course Agent เป๊ะ
- **Hypothesis:** เช็คลิสต์เชิงป้องกันแชร์ต่อได้ดีกว่าบทความสรุปเคสความสำเร็จ และดึงคนที่ "กลัวถูกหลอก"
  ซึ่งเป็นคนที่พร้อมจ่ายให้เจ้าที่พิสูจน์ตัวได้
- **ทำไมตอนนี้:** source ครบแล้วทั้งหมดในรายงาน Reese (มี URL ทุกข้อ) เขียนได้เลยไม่ต้องวิจัยใหม่ + กระแสยังอยู่
- **Effort:** 3–4 ชม. (Rae เขียน → Reese fact-check → Chris QA)
- **เหตุผลที่อาจล้มเหลว:** **เราเองก็ขายคอร์ส** — ถ้าน้ำเสียงเป็น "ตีคนนั้น" จะอ่านเป็นการดิสเครดิตคู่แข่งเพื่อขายของตัวเอง
  แล้วเสียเครดิตแทนที่จะได้ ทางแก้บังคับ: ห้ามเอ่ยชื่อบุคคลเป็นตัวร้าย, ต้องเอา 5 ข้อมาจ่อคอร์สตัวเองในย่อหน้าสุดท้าย
  และตอบให้ครบว่าเราผ่าน/ไม่ผ่านข้อไหน
- **Research questions:** คอร์ส agent ในไทยที่ขายอยู่มีกี่เจ้า ราคาช่วงไหน? · แพลตฟอร์มไหนที่คอนเทนต์แนวนี้เดินดี (Facebook/Blockdit/เว็บเรา)?
- **Format hint:** บทความเว็บ 900–1,200 คำ + การ์ดสรุป 5 ข้อ 1 ภาพ (Mind วาดใหม่ ห้ามใช้ภาพจากบทความต้นทาง)

### Idea 1.3 — "AGAPAE เปิดบ้าน": หน้าสาธารณะที่โชว์ระบบตัวเองแบบตรวจได้

- **คอนเซปต์:** เพิ่มหน้า/แท็บบน dashboard ที่มีอยู่แล้ว — อธิบายว่าระบบทำงานยังไง 3 ชั้น
  แล้วโชว์ตัวเลขที่ระบบเขียนเอง (จำนวนผลงาน, วันที่ล่าสุด, กลไกตรวจยังทำงานหรือไม่) พร้อมช่อง
  **"บทเรียนจากความพังของเรา"** ที่บันทึกเคสจริงเป็นรายการสั้น ๆ
- **ทำเพื่อใคร:** คนที่ลังเลจะซื้อคอร์ส/จ้างงาน + ใช้เป็น proof asset แนบใน Fastwork listing
- **Hypothesis:** ลิงก์เดียวที่กดเข้าไปเห็นระบบจริง แปลงคนสงสัย → คนถามราคา ได้ดีกว่าคำโฆษณา 10 บรรทัด
- **ทำไมตอนนี้:** dashboard + Firestore มีอยู่แล้ว, DESIGN.md มี token พร้อม → เป็นการ "จัดหน้าร้าน" ไม่ใช่สร้างระบบใหม่
- **Effort:** 4–6 ชม. (Vera วาง layout → Dale ต่อข้อมูล) — ควรทำ **หลัง** Idea 2.1 เพราะต้องมีของจริงให้โชว์
- **เหตุผลที่อาจล้มเหลว:** เปิดบ้านแล้วต้องดูแลให้ดูดีตลอด — ช่วงที่ระบบเงียบ 2 สัปดาห์ก็เห็นกันหมด
  และ Firestore ตัวนี้อ่านด้วย API key ที่ฝังในหน้าเว็บ = อะไรที่เขียนลงไปคือเปิดเผย
  → **ต้องเช็คทุกฟิลด์ว่าไม่มีชื่อลูกค้า/ชื่องานจริง/ตัวเลขต้นทุนหลุด** ก่อนเปิด
- **Research questions:** คนดู dashboard ตอนนี้มีจริงไหม (มี analytics หรือยัง)? · ควรโชว์อะไรที่ "ไม่สวย" ได้มากแค่ไหนก่อนเสียลูกค้า?
- **Format hint:** 1 หน้าในเว็บ dashboard เดิม ไม่แยก repo

## ทิศทาง 2 — ใช้ปรับปรุง AGAPAE เอง (มุมคุณค่า)

**ตอบโจทย์ตรง ๆ ก่อน: 3 อย่างที่โจทย์ถาม อันไหนคุณเป้ "รู้สึกได้" จริง**

1. **Trajectory testing / ตัวตรวจว่ากลไกยังทำงาน — รู้สึกได้ที่สุด** เพราะที่หายไป 6 สัปดาห์ไม่ใช่ฟีเจอร์
   แต่เป็น **สิทธิ์ที่จะเชื่อคำว่า "ผ่าน QA แล้ว"** ทุกงานในช่วงนั้นคุณเป้อ่านคำว่า "ผ่าน" โดยที่ไม่มีอะไรผ่านจริง
   — แต่คุณเป้จะไม่รู้สึกจาก "ชุดเทสต์" เขาจะรู้สึกจาก **ป้าย 1 บรรทัดที่เห็นทุกวัน** (Idea 2.1)
2. **Memory ที่ค้นได้ — รู้สึกได้อันดับ 2** อาการที่เจอคือถามซ้ำ/ระบบคิดใหม่เรื่องที่ตกลงแล้ว (index ครอบ 34 จาก 119 ไฟล์)
   น่ารำคาญจริงแต่ไม่ทำให้ของเสีย
3. **Generator/Critic loop ที่โค้ดหมุนเอง — รู้สึกได้น้อยสุด และอาจติดลบ** Dale ยืนยันว่าเรามี critic 2 ชั้นอยู่แล้ว
   (Reese + Chris) ที่ขาดคือ "ใครหมุน loop" ซึ่งวันนี้คือคุณเป้ — และคุณเป้เป็นคนอนุมัติทางแยกทุกจุดโดยเจตนา
   ทำให้ loop วนเองอัตโนมัติ = ไปแย่งจุดที่เขาอยากคุม แล้วได้ 3 รอบแก้ที่เขาไม่ได้สั่ง

### Idea 2.1 — "ป้ายสถานะความน่าเชื่อถือ" 1 บรรทัดบน dashboard  ⭐ ควรทำก่อน

- **คอนเซปต์:** บรรทัดเดียวที่ตอบว่า **"กลไกตรวจงานยังทำงานอยู่ไหม — ล่าสุดเมื่อไหร่"**
  สีเดียว ตัวเลขเดียว ไม่มีกราฟ ไม่มีแท็บ ถ้าเงียบเกิน 3 วันต้องเห็นด้วยตาทันที
- **ทำเพื่อใคร:** คุณเป้คนเดียว — แต่เป็นคนที่ต้องตัดสินใจจากคำว่า "เสร็จแล้ว" ทุกวัน
- **คุณค่าที่รู้สึกได้:** เปลี่ยน "หวังว่ามันทำงาน" → "เห็นว่ามันทำงาน" ถ้าไฟดับ รู้ในวันนั้น ไม่ใช่ 6 สัปดาห์ต่อมา
  และเป็นข้อเดียวที่ทำให้ความพังครั้งนี้ **เกิดซ้ำไม่ได้** แทนที่จะแค่ซ่อมครั้งนี้
- **ทำไมตอนนี้:** Dale #1 (P0 — **ยังรอ Kittanate อนุมัติ**) จะสร้าง log ของการยิง hook อยู่แล้ว → เอา mtime + จำนวนมาแสดงเพิ่มแรงน้อยมาก
  และผลพลอยได้คือ **ภาพหน้าจอที่ Idea 1.1/1.2/1.3 ใช้เป็นหลักฐานได้ทันที** (ของชิ้นเดียว ใช้ 2 ธุรกิจ)
- **Effort:** 1–2 ชม. ต่อท้าย Dale #1 (Vera 0.5 + Dale 1)
- **เหตุผลที่อาจล้มเหลว:** **ป้ายเขียวปลอม** — ถ้าตัววัดพึ่ง hook ตัวเดียวกับที่มันวัด มันตายพร้อมกันแล้วป้ายยังเขียว
  → เงื่อนไขบังคับ: ป้ายต้องอ่าน "เวลาล่าสุดที่มีสัญญาณ" แล้วเทียบกับเวลาปัจจุบันตอนเปิดหน้า
  (เงียบ = แดงเอง) ห้ามให้ hook เป็นคนรายงานว่าตัวเองสบายดี
- **Research questions:** เกินกี่วันที่เงียบถือว่าผิดปกติจริง (ดูจาก worklog ย้อนหลัง)? · ควรอยู่หน้าแรกของ dashboard หรือส่งเป็นข้อความตอนเช้า?

### Idea 2.2 — "เช็คก่อนนอน" คำสั่งเดียวจบ

- **คอนเซปต์:** ห่อ 5 บรรทัดใน appendix "วิธีตรวจซ้ำ 2 นาที" ของ Dale เป็นคำสั่งเดียว
  ที่คุณเป้พิมพ์เองได้ แล้วได้คำตอบ 5 บรรทัด ผ่าน/ไม่ผ่าน ไม่มีอย่างอื่น
- **ทำเพื่อใคร:** คุณเป้ — คนคุมระบบคนเดียวที่ต้องมีวิธีตรวจที่ไม่ต้องเรียก Dale มาขุดโค้ด
- **คุณค่าที่รู้สึกได้:** ความสงบใจแบบพิมพ์ครั้งเดียว ไม่ต้องจำว่าต้องดูไฟล์ไหน
- **ทำไมตอนนี้:** เนื้อหาเขียนเสร็จแล้วในรายงาน Dale เหลือแค่ห่อ = effort ต่ำสุดในไฟล์นี้
- **Effort:** ~1 ชม.
- **เหตุผลที่อาจล้มเหลว:** **ของที่ต้องจำว่าต้องรัน คือของที่จะตายเงียบรอบสอง** — ถ้าต้องพึ่งวินัย มันจะถูกรัน 3 วันแรกแล้วเลิก
  → ถ้าทำ ต้องผูกกับสิ่งที่เกิดอยู่แล้ว (จบเทิร์นแรกของวัน) ไม่ใช่เป็นคำสั่งที่รอคนนึกขึ้นได้
  ซึ่งถ้าทำแบบผูกอัตโนมัติ มันก็กลายเป็น Idea 2.1 → **ข้อนี้คุ้มเฉพาะในฐานะของแถมของ 2.1 ไม่ใช่งานเดี่ยว**

### Idea 2.3 — Index ที่ตอบได้ว่า "เรื่องนี้เคยทำแล้ว"

- **คอนเซปต์:** สารบัญผลงานที่สร้างเองอัตโนมัติทุกครั้งที่มีไฟล์ใหม่ (Dale #4) + บังคับให้ agent อ่านก่อนเริ่มงาน
  โดยแยกส่วนที่โค้ดทำไม่ได้ (โยง chain, flag เวอร์ชันซ้อน) ไว้ให้ Libby ทำมือในไฟล์ที่สคริปต์ไม่แตะ
- **ทำเพื่อใคร:** คุณเป้ (เลิกได้คำตอบที่ขัดกับที่เคยตกลงไว้) + ทุก agent ที่ต้องอ้างของเก่า
- **คุณค่าที่รู้สึกได้:** เลิกจ่ายค่า "คิดใหม่เรื่องที่คิดแล้ว" — วันนี้ 85 ไฟล์จาก 119 ค้นไม่เจอถ้าไม่จำ path เอง
- **ทำไมตอนนี้:** index ทำมือค้างมา 2 เดือน และมันจะค้างต่อไปเรื่อย ๆ เพราะไม่มีใครสนุกกับการทำสารบัญ
- **Effort:** ~2.5 ชม. (Dale #4)
- **เหตุผลที่อาจล้มเหลว:** **index ที่สดแต่ไม่มีใครอ่าน ก็ไม่ช่วยอะไร** — ถ้าไม่เขียนลง SOP/agent file ว่า
  "ก่อนเริ่มงานให้เปิดสารบัญก่อน" มันจะเป็นไฟล์สวยที่ไม่มีคนเปิด
  → ตัววัดความสำเร็จต้องเป็น "มีงานที่ถูกยกเลิกเพราะพบว่าทำแล้ว" ไม่ใช่ "index ครอบคลุม 100%"
- **⛔ สิ่งที่ห้ามทำในข้อนี้:** vector DB / semantic memory — Dale ชี้ว่าปัญหาเราคือสารบัญค้าง ไม่ใช่การจัดอันดับผลค้นหาแย่

## ทิศทาง 3 — ใช้กับงานโรงพิมพ์/ลูกค้าจริง

**ตอบก่อนว่าโครง 3 ชั้น map กับงานโรงพิมพ์ได้แค่ไหน — ได้ครึ่งเดียว และครึ่งที่ได้คือครึ่งที่มีเงิน**

- **Directives** = ความรู้กระดาษ/สเปก/กฎที่เรามีอยู่แล้ว (ชนิด vs แบรนด์, สูตรแปลงหน่วย, สเปกงานพิมพ์) → **map ตรง เราแข็งอยู่แล้ว**
- **Orchestration** = คนรับบรีฟและตัดสินใจว่างานนี้ทำท่าไหน → **คือคุณเป้ และไม่ควรยกให้ AI** ประสบการณ์ 40 ปีคือสินทรัพย์ ไม่ใช่คอขวด
- **Execution** = แบ่งเป็น 2 พวกคนละโลก:
  - **รับบรีฟ → คิดราคา → ปรีเพลส** = งานข้อมูล **AI ช่วยได้จริง** และเป็นจุดที่ Dale ชี้ว่าเป็นคอขวดจริงของโรงพิมพ์
    (ความเร็ว + ความถูกต้องของใบเสนอราคา ไม่ใช่จำนวนคนเข้าเว็บ)
  - **พิมพ์ → ส่ง** = ฟิสิกส์ AI แตะไม่ได้เลย
- **ข้อสรุป:** อย่าลอกสัดส่วนของเคสนั้น (ฝั่งดึงคน 10 : ฝั่งปิดการขาย 5) `[unverified]` มาทั้งก้อน
  ของเราต้องกลับด้าน — ลูกค้าโรงพิมพ์มาทาง LINE/โทรศัพท์/ลูกค้าเก่า 40 ปี ไม่ได้มาจากปากกรวยออนไลน์

### Idea 3.1 — "ตัวช่วยแปลงบรีฟเป็นสเปกที่คิดราคาได้"  ⭐ อันดับ 2 (อันแรกที่แตะเงินจริง)

- **คอนเซปต์:** ลูกค้าส่งบรีฟมาเป็นภาษาคน ("ทำแผ่นพับสวย ๆ พันใบ") ตัวช่วยนี้แปลงเป็น
  **(ก) สเปกเท่าที่บอกมา (ข) รายการที่ยังขาดและต้องถามกลับ** — ขนาด/จำนวนหน้า/กระดาษ/เคลือบ/พับ/จำนวน/กำหนดส่ง
  ออกมาเป็นข้อความพร้อมส่งกลับลูกค้าใน LINE ได้เลย
- **ทำเพื่อใคร:** คุณเป้ / คนคิดราคาที่โรงพิมพ์ (ใช้ภายในก่อน ไม่ใช่ของลูกค้า)
- **Hypothesis:** เวลาที่เสียในวงจรใบเสนอราคาส่วนใหญ่ไม่ได้อยู่ที่ "คิดเลข" แต่อยู่ที่ **ถาม-รอ-ถามอีก**
  ถ้าถามครบในรอบเดียว รอบการเสนอราคาจะสั้นลงและอัตราปิดจะขึ้น → วัดด้วยชีตนับมือที่ Addy วางไว้ใน BACKLOG แล้ว
  (คำขอราคา/สัปดาห์ + อัตราปิดใบเสนอราคา) โดยไม่ต้องมีตัวเลขต้นทุนโผล่ที่ไหน
- **ทำไมตอนนี้:** Dale ชี้คอขวดตรงนี้จากหลักฐานใน backlog ของ Addy เอง + โปรเจกต์ `PrintJob` (LINE → โฟลเดอร์งาน)
  และ `printorder` มีอยู่แล้ว → ต่อยอด ไม่ใช่เริ่มศูนย์
- **Effort:** 4–6 ชม. เฟสแรกเป็น skill + ชุดคำถามมาตรฐาน **ยังไม่ต้องมี MCP ยังไม่ต้องแตะฐานราคา**
- **เหตุผลที่อาจล้มเหลว:** ถ้าโมเดล **เดา** สเปกที่ขาดแทนที่จะถาม จะได้ใบเสนอราคาที่ผิด — ซึ่งแพงกว่าไม่มีตัวช่วยเลย
  → กฎเหล็กข้อเดียวของงานนี้: **ขาดคือขาด ห้ามเติมให้** · ความเสี่ยงข้อสอง: คุณเป้อ่านบรีฟเองเร็วกว่าอยู่แล้ว
  → ต้องทดลองกับบรีฟเก่า 10 อันก่อนสร้างอะไรจริง ถ้าไม่ชนะฝีมือคนก็ทิ้งไอเดียนี้
- **Research questions:** บรีฟที่เข้ามาจริง 20 อันล่าสุด ขาดข้อมูลข้อไหนบ่อยที่สุด? · รอบถาม-ตอบก่อนออกใบเสนอราคาปกติกี่รอบ?
- **Format hint:** skill ใน AGAPAE + แบบฟอร์มคำถาม 1 หน้า (ยังไม่ทำ UI)

### Idea 3.2 — เลิกให้ AI คิดเลขกระดาษเอง (มุมคุณค่าของ Dale #5)

- **คอนเซปต์:** ย้ายข้อมูลวัสดุที่วันนี้ฝังอยู่ในไฟล์เว็บ **2 ไฟล์ที่ต้องเหมือนกันเป๊ะ** ออกมาเป็นแหล่งเดียว
  แล้วค่อยห่อเป็นเครื่องมือที่ทุก agent เรียกใช้ได้ — จุดสำคัญเชิงคุณค่าคือคำตอบต้องบอกได้ทุกครั้งว่า
  **"อันนี้ราคายืนยัน" กับ "อันนี้ค่าประมาณ"** ไม่ปนกัน
- **ทำเพื่อใคร:** คุณเป้ + ทุก agent ที่แตะเรื่องกระดาษ (Reese, Rae, Addy)
- **คุณค่าที่รู้สึกได้:** เลิกลุ้นว่าโมเดลคิดเลขคลาด และเลิกกลัวกับดักแบรนด์ vs ชนิดกระดาษที่เคยพลาดจริง
  + แก้ราคาครั้งเดียวไม่ต้องแก้ 2 ไฟล์
- **ทำไมตอนนี้:** เฟสแรก (แยกข้อมูลออกจาก HTML) คุ้มด้วยตัวเองแม้ไม่ทำอะไรต่อ
- **Effort:** เฟส A ~3 ชม. · เฟส B ~4 ชม. (ทำ B เมื่อ A นิ่งแล้วเท่านั้น)
- **เหตุผลที่อาจล้มเหลว:** เว็บที่ใช้จริง + โฮสต์แบบ static = path ผิดแล้วหน้าว่างทันที (เคยเจอมาแล้ว)
  → เฟส A ต้องผ่าน Chris QA ก่อนแตะเฟส B · และถ้าห่อเครื่องมือรอบข้อมูลที่ยังซ้ำ 2 ที่ จะได้แหล่งความจริง 3 ที่ แย่กว่าเดิม
- **⚠️ ข้อบังคับ:** ข้อมูลชุดนี้อยู่ในเครื่อง/ในเว็บที่เราคุมเท่านั้น **ห้ามหลุดเข้าบทความ คอนเทนต์ หรือของที่ขายลูกค้า** ทุกกรณี

### Idea 3.3 — ขายเป็นบริการ: ชุด agent สำหรับ "อาชีพที่ต้องเสนอราคาทุกวัน"

- **คอนเซปต์:** ชุดพร้อมใช้ตัวที่ 3 ของ Course Agent (วันนี้มี founder / merchant) = **"ผู้รับงานที่ต้องเสนอราคา"**
  — ร้านป้าย ร้านเสื้อ ช่างเฟอร์นิเจอร์ ออกาไนเซอร์ ธุรกิจที่ทุกงานต้องคิดราคาใหม่
  ขาย **โครงการถามคำถามและกระบวนการ** ไม่ใช่สูตรหรือฐานราคาของเรา · ใช้ AgentSuchart เป็นเวปสาธิต
- **ทำเพื่อใคร:** ลูกค้า Course Agent แพ็กบน + ลูกค้าโรงพิมพ์ที่เห็นระบบเราแล้วอยากได้ของตัวเอง
- **Hypothesis:** SME ไทยที่ปวดหัวเรื่องเสนอราคาจ่ายง่ายกว่า SME ที่ปวดหัวเรื่อง "ยังไม่รู้จะใช้ AI ทำอะไร"
  เพราะปัญหาชัดและวัดผลได้เอง → ทดสอบด้วยการเสนอชุดนี้กับลูกค้าที่คุยอยู่ 3 ราย ก่อนสร้าง
- **ทำไมตอนนี้:** Course Agent ค้างอยู่ที่ "ชุดพร้อมใช้อีก 4 อาชีพ" อยู่แล้ว → นี่คือชุดที่เรามีของจริงหนุนหลังที่สุด
  และเป็นทางออกจากการต้องแข่งกับ blueprint ที่ขายด้วยจำนวน agent
- **Effort:** 6–8 ชม. (ชุด starter kit 1 อาชีพ + เคสสาธิต) — **ต้องรอ Idea 3.1 ใช้จริงในโรงพิมพ์ก่อน** ห้ามขายของที่เรายังไม่ใช้เอง
- **เหตุผลที่อาจล้มเหลว:** เส้นแบ่งบางมากระหว่าง "ขายกระบวนการ" กับ "สอนคู่แข่งคิดราคา" — ถ้าเผลอใส่ตัวอย่างจากงานพิมพ์จริง
  เท่ากับยกความได้เปรียบออกไปฟรี ๆ → ตัวอย่างในชุดขายต้องเป็นอาชีพอื่นทั้งหมด ไม่ใช่งานพิมพ์
  · ความเสี่ยงข้อสอง: บริการแบบนี้มีหางยาว (ลูกค้าถามต่อ 6 เดือน) ซึ่งคนคุมคนเดียวรับได้จำกัด
- **Format hint:** โฟลเดอร์ `05-starter-kit/quoter/` + 1 หน้าในเวปสาธิต
